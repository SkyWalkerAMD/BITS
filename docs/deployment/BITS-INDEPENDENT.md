# BITS 0.4.2 安装、升级与网页操作

版本 0.4.2。所有控制端和节点共用以下流程，与主机名、IP 地址无关。RPM / DEB 自动处理正常升级；首次安装后仅需初始化中心或导入节点连接文件。BITS-o、OCRUN 与 0.3.0 使用不同协议，不套用本版原地升级。

## 需要安装什么

新增“硬件信息”入口位于节点卡片、节点详情和实时监控页。按分类查看或搜索 `sckocp info` 字段，约 30 秒采集一次，无需创建批次。内存时序沿用数据接口的 Primary 导出范围。中心保留上次成功快照；离线或采集失败时保留历史信息并显示采集时间。该功能需要节点端也升级至 0.4.1。

中心安装 bits-center 的 RPM 或 DEB；节点安装 bits-node 的 RPM 或 DEB，节点包包含固定版本工具及本地采集/报告适配器。节点仍单独安装原版 sckocp，并在 BITS 以外按原流程完成授权。BITS 不保存激活码，不连接或管理激活数据库。

RPM 版本为 0.4.2-1.el8，DEB 为 0.4.2-1；程序显示 0.4.2。先核验 SHA256SUMS，再用系统包管理器安装对应格式；现有安装按下文升级，保留配置、连接身份及数据。

## 新中心，root

先安装中心包：`dnf install ./bits-center-0.4.2-1.el8.x86_64.rpm`；Debian / Ubuntu 使用 `apt install ./bits-center_0.4.2-1_amd64.deb`。然后查看本机地址：

    bits-center network

使用这台中心的实际内网地址和允许网段初始化一次，成功后自动启用并启动服务：

    bits-center setup --address 192.168.50.10 --network 192.168.50.0/24 --apply

默认仅使用 TCP 443。应用本身校验来源网段；已有主机防火墙仍需允许该网段访问 443，安装程序不会修改网卡、网关、DNS 或关闭防火墙。节点不需要开放入站端口，数据库不监听网络。不需要 Redis 6379、rsync 873 或 HTTP 80。

管理员连接材料保存在 /root/.bits/admin.json，仅 root 可读，其中 token 是 BITS 管理口令，与 sckocp 激活码无关。浏览器访问中心 HTTPS 地址，用该管理口令登录。首次生成的是专用自签证书；通过可信渠道核验并安装证书信任，不能忽略证书验证。节点导出的连接文件固定信任该证书；更新证书需要明确重新分发信任材料。

## 网页登记节点

点击“添加节点”，填写实际 hostname 和稳定资产编号。下载该节点专属连接文件，使用可信 SSH/SFTP 等方式传到节点 /root，设为 root 属主、0600 权限。不要将该文件放 Git、公共下载目录或结果目录。

也可用命令行：

    bits-center node-add --node TEST-NODE --serial ASSET-001 --keep-on --output /root/TEST-NODE.bits.json

没有 --keep-on 时，成功交付后沿用 30 分钟空闲关机策略。登录用户、运行任务或待处理失败阻止关机；断网不触发关机。

## 新节点，root

安装节点包：`dnf install ./bits-node-0.4.2-1.el8.x86_64.rpm`；Debian / Ubuntu 使用 `apt install ./bits-node_0.4.2-1_amd64.deb`。导入一次该节点连接文件，成功后自动启用并启动服务：

    bits-node enroll --file /root/TEST-NODE.bits.json

服务只等待明确授权，不从待办列表自动执行压测。原 sckocp 的交互硬件查看仍使用 sckocp；BITS 不提供新的硬件交互命令或远程 sckocp 控制入口。

## 开始与结果

工作台包含六个入口：

| 入口 | 可完成的操作 |
| --- | --- |
| 任务分发 | 多节点任务组、可达状态、BMC 绑定、共用任务模板、确认开机与开始、逐台结果、分发操作记录 |
| 运行总览 | 在线 / 运行 / 待处理 / 已交付计数、优先显示进行中节点与最近批次 |
| 测试节点 | 按名称自然顺序排列、搜索、按在线与运行状态筛选、每页 24 台、查看节点关联批次 |
| 压测批次 | 三步编排向导、短程 / CPU / 内存起始计划、保存草稿、明确开始、填写原因取消、核对现场后关闭未完成批次 |
| 结果与报告 | 搜索已交付批次、HTML / Excel、原始分段、工具日志及带 SHA-256 的完成回执 |
| 部署与操作 | 节点登记与专属连接文件下载、首次接入命令、异常处理与结束后行为指引 |

节点心跳约 5 秒；浏览器实况轮询约 2 秒，常规列表约 6 秒。卡片显示当前工具、每步及全批次时长预算、CPU 温度、Pkg 功耗、平均核心频率。详情显示最近 180 个主采样的温度 / 功耗趋势，以及内存最高温度、DRAM 功耗、PSU 输入、VCCIN、VID、TjMax 和系统负载。

主采样约 2 秒，内存 / PSU / VCCIN 等补充信息约 30 秒，两类时间分别标明。网页更新时间不等于传感器内部读数年龄。心跳超过 20 秒按系统未连接处理，节点卡片另结合 BMC 观测显示电源状态；采样接收超过 15 秒或观察时间超过 20 秒标为过期。旧值可供参考，不能视为当前硬件状态。执行完后的批次缓存明确标为最后读数；完整统计始终以封存的报告和证据为准。

页面在不可见时暂停轮询，重新打开后同步。中心重启会清空短期趋势缓存，随后从节点继续接收；已经封存的数据和报告不受影响。浏览器必须重新确认连接后才能显示在线状态。网页实时数据不新增 sckocp 命令，不传递授权或非 Primary 时序。

### 系统在线时持续监控（0.4.0）

0.4.0 支持系统在线时持续监控，空闲节点也可查看。此能力需要中心与节点都升级至 0.4.0；进行中的压测应先完成，升级时保留已有连接配置、BMC 绑定和报告。

在“运行总览”或“测试节点”点击节点卡片的 **实时监控 ↗**，即可进入该节点固定的监控页面。无需创建或开始压测批次：空闲时显示“日常硬件监控”，开始压测时自动显示当前批次读数，执行结束后恢复日常读数。批次详情中的 **硬件实时监控** 保留该批次的最后读数，可点击 **节点当前状态 ↗** 返回实时页面。

日常监控仍要求节点服务运行、与中心连接且 sckocp 已正常安装并授权。它只保留最新硬件快照和最近 180 次汇总趋势，不产生压测报告，也不将日常读数写入旧批次证据。关机/断线明确显示最后读数，采集失败显示不可用；恢复后继续更新。原有成功交付后 30 分钟空闲关机策略继续生效，日常监控不会阻止该策略；需要持续开机的节点应使用“完成后保持开机”。

本版还调整 VCCIN / PSU 补充采集：保留传感器目录缓存，给目录探测和读数分别设置受控时间预算，不缓存旧测量值。终端能读到并不保证每次补充采集成功；失败时显示“—”，以补充读取时间和原始采样判断，不补造缺值。

### 批次硬件实况（alpha.3 起）

在“运行总览”或“测试节点”找到正在压测的机器，点击 **实时监控 ↗**；也可在批次详情点击 **硬件实时监控**。无需登录节点终端，也不会额外启动采集。

- 整机：CPU 最高温度、全部插槽的 Pkg 功耗、PSU 报告的整机输入、核心平均频率、系统负载。
- 每个插槽：型号、核心/线程数、基础与当前频率、温度、TjMax、VID；补充区域显示 VCCIN、Mesh、内存速率/容量/使用量/DIMM 数量/最高温度、DRAM 功耗、PC2/PC6。
- 每个 CPU 编号：核心矩阵或详细表格，可按插槽筛选，按数字顺序排列；表格包含频率、温度、VID、C0/C6。超过 64 个编号时分页。当前 sckocp v1 JSON 未提供 IRQ，明确显示“未提供”。
- 主采样和补充读数分别标明时间；补充读取失败或老化不靠新主采样伪装成新值。失联、读数过期、采集不可用、采集结束均有单独提示。矩阵色条表示 C0 比例，不判定硬件合格。

中心仅保存每节点最新硬件快照。逐核心数组只在打开该批次时返回，不进入全节点列表或 180 点汇总趋势。实时页面不输出任何时序或授权材料；报告既有的 Primary 时序规则保持不变。旧节点只发汇总指标时，页面提示升级，不补造逐核心数值。该功能需要 alpha.3 的中心与节点配套；本版安装包仍为两个角色包。

### 网页操作改进（alpha.4）

- 桌面左侧导航和顶部栏随视口固定；左上角可收起或展开导航，折叠偏好保存在当前浏览器。屏幕较矮时导航区域可独立滚动。整页长截图只在首屏绘出固定栏；Release 的 hardware-scrolled.png 是滚动后的视口截图。
- 手机和窄屏使用左上角的导航抽屉，全部栏目保留文字；点击栏目、关闭按钮或 Escape 可关闭。弹窗内的键盘焦点不会进入背景操作。
- 硬件页的分区栏可快速跳转到整机、插槽、逐核心和趋势。顶部可立即刷新，长页右下角可返回顶部；两者均不会启动新采集或任务。
- 批次每页 25 条，报告每页 18 份，节点仍为 24 台。筛选重置分页；自动刷新保留当前分页、核心表格滚动与焦点。浏览器返回上页时恢复本会话的阅读位置。
- 趋势图显示纵轴刻度，按采样时间分布绘制。无读数与超过 10 秒的采样间断不连线；单点也可见。实时缓存仍不替代最终报告。
- 提交中禁用表单修改、重复提交和关闭，等待明确响应；发生失败时保留输入。超时只代表未确认服务器状态，请先核对已保存的节点或批次，不要把超时当作提交失败后反复创建。

中心和节点安装包版本保持配套发布。alpha.5 增加任务组、批量开始事务和 BMC 开机等待，仍以操作者明确开始为前提；原生 sckocp 权限、采样命令和历史证据保持原样。验证范围以本版 VERIFICATION.json 为准。

“复制计划为新草稿”只复制工具和时长，不重新执行旧批次。网页操作保留后端认证、节点归属、尝试编号与单节点单批次校验。首次软件安装、证书信任、主机服务启动和无法自动确认的进程故障检查仍由对应机器 root 执行，不把网页做成远程终端。

网页创建批次，选择工具和每步时长。创建后先等待，核对节点再点击“开始”。初验建议 stress 10 秒 → stress-ng 10 秒；这会实际压测，只能用于指定空闲节点。

命令行等价操作：

    bits-center batch-add --node TEST-NODE --label FIRST-CHECK --steps stress=10,stress-ng=10
    bits-center start --batch 输出的批次编号
    bits-center status

查看单个批次的步骤、文件和结果使用 `bits-center status --batch 批次编号`。概览只返回简短状态，避免长期积累的详细数据拖慢网页。

批次内同工具可以重复出现且使用不同预算。开始授权 5 分钟未接受会取消；重启不会自动执行已过期授权或重复已有尝试。取消需指定原因：

    bits-center cancel --batch 批次编号 --reason "操作员取消本次验证"

网页分别显示压测执行、监控质量、报告和交付。节点保留带序号及步骤编号的 telemetry 分段、工具输出、MON 导出、Excel、HTML/JSON 报告；中心核验文件后生成独立 receipt.json。上传支持分块续传，节点仍对远端完整副本核验 SHA-256。非 Primary 时序和授权材料不得出现在任何交付文件中。

节点状态：

    bits-node status
    journalctl -u bits-node.service -n 60

有待报告/上传步骤时，常驻服务只重试证据处理，不重新运行压测。无法恢复的批次保留现场，由操作员确认节点工作进程已停止后，使用网页“关闭未完成”并填写原因；不会产生成功回执。

## 批量分发与按需开机（alpha.5）

首次仍要在节点安装并配置 `bits-node`、在 BITS 之外完成 sckocp 授权，并启用 `bits-node.service`。此后可从网页选择多台节点，不用逐台 SSH 启动任务。

1. 进入 **任务分发**。查看节点的系统连接和 BMC 状态；后台每轮检查后间隔 10 秒查询已绑定的管理口，最多 16 个并发请求；不可达管理口会延长整轮检查。显示的是最近查询结果，超过 90 秒不再作为可达依据。
2. 需要唤醒的节点先点击 **绑定 BMC**：填写对应管理 IPv4、专用 IPMI 账号和密码。保存只查询状态。优先使用 Cipher 17；设备明确不支持时再选择 Cipher 3。节点有未完成批次时禁止更改绑定。
3. 点击 **新建任务组**，选择 1–200 台可达且无未完成批次的节点。系统在线、BMC 确认关机、BMC 确认开机但系统未连接分别显示；不可达节点不能选择。无法仅靠网络断言不可达的原因是没接电。
4. 编排共用步骤和时长；支持重复工具、每台最多 128 步及 31 天预算。可以保存模板；最近 200 个模板可复用，模板复制到任务组后不会改变已保存计划。
5. 保存后仍是草稿。任务组里勾选本次要开始的节点，点击 **确认分发并开始**。系统再次检查整个所选集合，有一台条件变化则整次授权不提交；操作者可明确调整选择后重试，不会静默跳过。未选草稿保留且不自动开始。
6. 系统已连接的节点收到本批次授权；关机节点先用 IPMI 请求开机，已开机但系统未连接的节点只等待。等待最多 10 分钟；BMC 返回成功不代表系统已启动。只有收到本次开始请求之后的新认证心跳，且没有更新的关机观测，才授权压测，随后节点自身仍进行工具、采集和报表执行前检查。
7. 任务组汇总每台执行、监控质量、报告及交付状态。可打开每台批次和实时硬件页面；一台执行失败不会取消其他台。按节点选择取消，不会强制断电；已发出的开机指令不能撤回，运行中任务的停止以节点确认结果为准。

只有此明确授权的任务组才触发开机。电源等待占用节点名额，防止重复批次；中心重启后根据持久化意图继续等待或记录失败，不会盲目重发结果不明的开机指令，也不会重跑压测。超时或未确认开机会标记 `needs_attention` / `not_started`；查看原因，核对机器后“关闭未完成”，需要测试时复制或新建计划再次明确开始。不要用重复点击绕过待处理状态。

新增网络方向是 **中心 → 已绑定 BMC：UDP 623**，只需在管理网络允许指定中心访问指定管理口；不新增节点操作系统入站端口。中心包依赖发行版 `ipmitool`；调用固定 LANplus `mc guid`（自动绑定身份核对）和 `chassis power status/on`，不接受任意 IPMI 参数，不提供断电、重启、原始命令或 sckocp 权限管理。参数依据 [ipmitool 官方手册](https://github.com/ipmitool/ipmitool/blob/master/doc/ipmitool.1.in)。

BMC 凭据保存在中心 `/var/lib/bits/center/bmc.json`，权限 0600，目录 0700；只允许服务账户和管理员读取，不回传密码、不放入节点连接文件、任务计划或报告。数据库和配置备份也必须按凭据材料保管。使用独立管理网和专用 OPERATOR 账户；部署者需先核对节点与管理口映射。实际主板的 IPMI 支持、电源状态及开机到系统连接的耗时需要现场验收。

CLI 保留相同入口：`bits-center dispatch-nodes` 查看可达性；`bits-center status --group ID` 查看组；`bits-center group-add --file /root/plan.json`、`group-start --group ID --file /root/start.json`、`group-cancel --group ID --file /root/cancel.json` 使用与网页相同事务。JSON 文件须是可信目录中的 0600 常规文件。创建的字段是 `request_id`（32 位十六进制随机标识）、`label`、`nodes`、`steps`；开始字段是新 `request_id`、本组 `batches` ID 数组、明确的 `wake` 布尔值；取消另需 `reason`。同一请求原样重试不会二次分发，改变请求内容必须使用新标识。

## 添加节点时使用自定义 BMC 模板（alpha.7）

在 **添加节点 → BMC 凭据模板 → 使用模板** 选择中心已有模板，无需逐台重新填写 BMC 账号密码。可以查看用户名、Cipher、管理网段和适用条件；模板密码不回显。没有合适模板时，点击同一窗口的 **新建模板**，填写并保存后会自动选中，已输入的节点名与资产编号保留。

点击 **创建并下载连接文件**，中心同时保存节点身份和模板选择。专属连接文件仍只含节点接入所需的六个字段，不含 BMC 模板、用户名或密码。节点首次接入并上报管理口后，中心仅使用选定模板核对身份和绑定；所选模板仍须符合管理网段、节点名前缀及主板型号条件。模板停用、缺失、条件不符或管理口不唯一时显示原因，不会改用其他模板尝试。

选择 **自动匹配模板** 则沿用下节的规则，只有唯一匹配时才绑定。新建模板、添加节点和保存选择均不会开机。网页的任务分发与节点详情可查看接入时选择的模板。CLI 对应参数为 `bits-center node-add --node TEST-001 --serial ASSET-001 --bmc-profile default --output /root/TEST-001.bits.json`；模板需先在中心创建，省略 `--bmc-profile` 使用自动匹配。

模板修改只作用于之后的绑定，包括已登记但尚未完成绑定的节点；已经绑定的节点继续保留绑定时的凭据。以后更换账号时，可新建另一模板供新节点使用，也可编辑原模板。BITS 保存的是连接凭据，不修改设备本身的 BMC 账号。

## 自动绑定 BMC 与统一节点状态（alpha.6 起）

账号统一或按机型统一时，在 **任务分发 → 自动绑定设置** 创建凭据模板：填写标识、允许的 BMC 管理网段、IPMI 用户名、密码与 Cipher。统一账号可只限制管理网段；按机型区分时，再填写节点名前缀或主板型号（完整匹配）。多个条件同时生效，留空的可选条件不参与匹配。避免同时启用范围重叠的通用模板和机型模板；系统遇到多个匹配会停下来，不轮流尝试密码。

节点升级至本版、首次开机接入且空闲后，会通过本机内核 IPMI 接口读取 BMC GUID、管理 IP/MAC 和主板型号。节点包新增发行版 `ipmitool` 依赖；固定读取 `-I open mc guid` 和 `lan print 0..11`，不扫描内网、不读取或修改账号、不涉及 sckocp 权限。发现总超时 20 秒，空闲时约每小时刷新；压测、报告和上传期间不执行发现。

中心仅使用最近 24 小时上报且唯一匹配的管理口/模板，远程核对同一 GUID 并查询电源状态后保存绑定。地址或 GUID 被多台节点认领、地址已绑定其他节点、缺少 GUID、本机接口不可用或无法完成查询时，保留手工处理入口。GUID 用于检查映射一致性，不替代管理网隔离与可信节点。绑定及保存模板均不发送开机指令。

自动核对失败会保存原因，相同发现与模板不会因网页刷新、心跳或中心重启反复试密码。检查网络、权限、Cipher 和映射后，点击该节点的 **重试自动绑定**（至少间隔一分钟），或修改模板后重新核对。编辑模板时密码留空表示保留原密码；网页不会回显密码。停用或修改模板仅影响后续自动绑定，已有绑定不自动覆盖；现有手工绑定继续使用。如需更新已有绑定，请在节点没有未完成批次时使用 **更新 BMC**。

模板、发现与核对记录保存在中心 `/var/lib/bits/center/bmc-auto.json`，0600，所在目录 0700；已绑定凭据仍在 `bmc.json`。模板密码不下发节点、不进入任务或报告。备份/清理时将这两个文件一同纳入中心私有数据处理。最多 16 个模板、200 台节点。

运行总览和测试节点与任务分发使用相同的 BMC 观测：**已关机 · 可唤醒**、**已开机 · 等待系统**、**状态待确认**分别显示。总览“可达节点”包含系统在线或管理口确认可达的节点，旁边另列系统在线与已关机数量。管理口观测超过 90 秒或浏览器失联，不继续按可达计数；不会仅因节点程序没有心跳就断言机器断电。旧中心或旧节点不能提供自动发现，两端需配套升级。

## 手动单台 / 批量唤醒（0.4.1）

已绑定 BMC 且管理口可达时，在节点卡片或硬件实时监控点击 **唤醒机器**，确认机器名单后开始。多台机器可在 **任务分发 → 节点可达状态** 勾选后点击 **唤醒所选机器**，一次最多 200 台。它只负责开机和等待系统连接，不创建批次或运行压测。已经在线的机器跳过；有未完成任务或其他唤醒操作的机器不能重复提交。

在同页“唤醒记录”逐台查看结果。开机命令被接受不代表系统已连接；节点新心跳到达后才显示“已连接”，超过 10 分钟显示超时。状态不明或请求中断时不会盲目重发，请先检查 BMC、系统启动和节点服务。

手动唤醒的 **0.4.1 节点** 会保持开机，以便日常监控；此状态在节点和中心重启后保留。下一次明确开始压测后解除该临时保持，按原“完成后保持开机”设置执行。0.4.0 节点不支持这个保持策略，使用前应升级。中心需要能访问 BMC UDP 623，节点服务需开机启动，节点到中心的路由需在重启后继续有效。

## 单条 / 批量永久删除（0.4.1）

在 **结果与报告** 点击一份报告的 **删除**，或勾选多份后点击 **删除所选**。**压测批次** 和批次详情也有相同入口。筛选 / 翻页会保留选择，工具栏显示其他页的选择数量；确认窗口列出全部批次及节点，一次最多 200 项。

删除对象是整个已结束批次及其中心证据：批次记录、事件、HTML / Excel、遥测、日志和回执一起永久清理，没有回收站。节点本地副本和管理员独立备份不会被删除。仅允许“已核验交付”“已取消”“已关闭未完成”；草稿先取消，运行、等待开机、上传、待处理中的批次禁止删除。混入不允许删除的批次时整次请求不提交。

页面下方显示清理进度；中心中断后继续未完成清理，失败时可检查中心日志再点击“重试清理”。删除后下载链接失效，空任务组一同移除。中心仅保留必要的 ID、归属与删除进度，阻止节点迟到上传将证据重新建立；本操作不提供介质安全擦除。

## 通用 RPM / DEB 升级

已安装 0.4.0 或 0.4.1 时，在对应机器上以 root 执行一条命令：

| 角色 | RPM | Debian / Ubuntu |
| --- | --- | --- |
| 控制端 | `dnf upgrade ./bits-center-0.4.2-1.el8.x86_64.rpm` | `apt install ./bits-center_0.4.2-1_amd64.deb` |
| 节点 | `dnf upgrade ./bits-node-0.4.2-1.el8.x86_64.rpm` | `apt install ./bits-node_0.4.2-1_amd64.deb` |

RPM 也可统一使用 `dnf install ./包名.rpm`：未安装时安装，版本较旧时升级。下载包所在目录可以任意选择。这里使用本地包；没有配置 BITS 软件源时不能省略文件路径。

包内自动检查未完成工作、停服、创建私有完整备份、替换软件并恢复原本运行的服务。运行、授权等待、唤醒、报告上传、待处理批次或未完成清理会阻止升级；处理完成后重新执行同一命令即可。不会为了升级取消压测。原本停止的服务保持停止，开机启动设置保留。中心会等待 HTTPS 就绪，节点检查配置、工作进程文件和服务状态；节点是否已连接中心仍以网页显示为准。

配置、TLS 身份、BMC 凭据模板和报告继续使用，不需要重新 `setup` 或 `enroll`。备份为 `/var/backups/bits/center/时间编号/before.tar` 或 `/var/backups/bits/node/时间编号/before.tar`，包含该角色配置、实际数据目录及中心管理员连接文件；中心同时包含数据库、WAL/SHM、BMC 配置和全部证据。目录 0700、文件 0600。保留每次备份，由管理员按保留策略清理；数据较多时需预留相应空间。

备份或升级前检查失败会保留旧包、恢复原服务并报错。文件解包或新服务启动失败时，保留备份和维护记录，检查包管理器输出及 `journalctl -u bits-center` / `journalctl -u bits-node`；修复原因后重新安装同一版本（RPM 使用 `dnf reinstall ./包名.rpm`，DEB 使用 `apt install --reinstall ./包名.deb`）。不跳过安装脚本，不直接降级打开新数据库。

首次初始化与节点导入默认启动服务。制作镜像或使用自定义服务时可加 `--start=false`；常规升级识别服务的 `--config` 参数和中心配置中的实际数据目录。自定义 shell 包装器或无法识别的启动参数会明确报错，保留现场。未配置的新系统支持离线镜像安装，已配置系统的自动维护要求 systemd 正常运行。

从 0.4.0 升级时，中心仍执行 schema 3 到 4 的事务迁移。旧版本拒绝新库，回退需恢复升级前完整快照及对应旧包。本版验证覆盖 0.4.0 / 0.4.1 的 RPM / DEB 实包升级、重复安装、服务状态保留、忙时拒绝和备份故障恢复。

## alpha.5 / alpha.6 的历史数据库升级

先完成所有已授权、运行和待处理批次，备份中心私有配置及数据。分别停止对应角色服务、安装本版同角色 RPM/DEB、执行 `systemctl daemon-reload`，再启动服务。中心数据库从 schema 2 事务升级到 schema 3，将接入模板选择与节点身份一起保存。有已有节点时，升级前自动生成一致性的 `center.sqlite.before-bmc-enrollment-v2`（0600）；如果该备份已存在，停止迁移并保留现场检查，不盲目删除重试。已有节点、批次、证据、模板和手工 BMC 绑定保留，已有节点继续沿用原匹配方式。

历史 alpha.7 的“添加节点选择模板”只要求升级中心，alpha.6 节点的管理口发现可继续使用。0.4.0 日常监控需要中心与节点同时更新，不能沿用这一旧版升级范围。网页升级后使用 Ctrl+F5 刷新。

关机节点可在中心更新后显示 BMC 状态，但它必须安装本版节点包并至少开机接入一次才能自动发现管理口。远程唤醒后自动接任务，还需节点服务开机启动、到中心的路由在重启后继续有效；临时 `ip route add` 和只执行 `systemctl start` 不满足这一条件。试点不要为升级重新初始化或覆盖原连接文件。

旧中心会拒绝 schema 3，不能直接用旧包打开升级后的数据库。回退时停止服务，保留当前全部数据后使用升级前完整快照及对应旧包；自动生成的数据库备份不能替代含凭据、证据和配置的完整快照。

## alpha.4 到 alpha.5 的历史迁移说明

先确认所有已授权、运行和待处理批次已妥善结束，在对应机器停止服务，再用包管理器安装本版同角色 RPM/DEB；升级后启动服务。不要在进行中的压测中更换节点包。数据库由 schema 1 事务迁移至 schema 2；有节点或批次的旧数据库迁移前，会在同目录生成一致性的 `center.sqlite.before-dispatch-v1`，0600。节点身份、旧批次和证据保留。已有同名备份时停止迁移并保留现场，不能盲目删除后重试。

旧版程序拒绝 schema 2。回退需先停止中心，完整保留本次数据目录（包括 WAL、证据和 BMC 配置），恢复升级前独立备份的数据目录及对应旧包。迁移后的新任务组和新批次不会出现在旧快照中；不能把旧主库覆盖到运行中的目录或与新 WAL 混用。本版新增的自动备份是数据库迁移保护，不代替升级前完整快照。

## 现场最小验收

在新 BITS 测试中心的网页管理员会话操作，选择两台明确空闲且允许开机的已登记节点：一台系统在线，另一台正常关机但 BMC 有电可达。绑定 BMC 后确认状态分别为“系统在线”和“已关机可唤醒”。新建任务组，`stress=60`、`stress-ng=60`，勾选两台并确认开始。预期：关机节点自动开机并连接；每台只执行一次，各生成 HTML/Excel/回执且独立核验交付。第三台已知断电测试机应显示不可达并无法选择。不要用断开生产网络或给正在压测的机器断电来验证故障。

云端使用模拟 BMC 驱动验证开机、等待、超时、重启与取消；浏览器使用一台 Linux worker 和一台协议模拟节点验证批量授权。上述物理开机验收尚需现场完成，不能把模拟结果当作主板兼容性证明。

## 停用、保留证据与回退

本版验证 0.4.0 / 0.4.1 包升级；更早 alpha 版本建议先使用 0.4.0 的既有升级流程。不提供 0.3 / OCRUN 原系统原地迁移、统一身份登录、高可用、节点登记凭据网页轮换或定期自动数据库备份。BMC 模板可在网页编辑，但不会修改设备账户或覆盖已有绑定。节点登记凭据与 sckocp 权限独立。首次配置中断时保留生成文件供检查，确认状态后再恢复。

先取消当前批次并确认已结束，再停止对应服务。未确认的进程残留不能通过强制卸载绕过。

    systemctl disable --now bits-node.service
    systemctl disable --now bits-center.service

分别在对应机器执行，然后使用 dnf remove 或 apt remove 移除对应角色包。配置及 /var/lib/bits 中的数据库、节点意图和证据保留。回退前停服并另存当前完整数据，使用升级前快照与对应旧包恢复；不要将不同时间的主数据库与 WAL 混用。包管理检查不能代替完整一致性备份。
