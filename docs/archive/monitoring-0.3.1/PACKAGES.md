# 原版 0730 的三个独立分发包

现有管理服务器继续使用原来的操作系统和 0730 OCRUN。接入 sckocp 时，只在被测设备安装采集插件；第三方软件可以另外使用独立本地接口。

| 包 | 用途 | 使用位置 |
| --- | --- | --- |
| `ocrun-manager-0730-original.tar.gz` | 用户提供的原始 `0730` 完整归档的逐字节副本，保留原有功能 | 留存、分发原工具集；现有管理服务器无需重新安装 |
| `mon-sensors-plugin-0.12.8.run` / `.tar.gz` | 给已有 0730 设备端增加独立采集命令，兼容旧任务、日志和上传；`.run` 自动解包安装 | 被测设备 |
| `sckocp-api-0.3.1.run` / `.tar.gz` | 供其他软件读取已激活的原版 sckocp；`.run` 自动安装命令和 SDK | 安装 sckocp 的同一台设备 |

## 原版管理端归档

`ocrun-manager-0730-original.tar.gz` 只是原始 `0730` 文件的分发名称，大小为 **1,563,646,537 字节**。它保留整个原版工具集，包括管理功能和工具依赖，**没有裁剪成专用服务器安装器**，也不包含本次新增插件。其原有部署方式和依赖要求保持不变。

当前管理服务器已运行 0730，无需重新解压覆盖或运行任何新版服务器安装器。这个包用于保存和分别交付原件。分发时用对应的大小及 SHA-256 校验记录核对文件；重新命名不代表重新打包。

## 设备采集插件

插件包用于已经安装 0730 的设备，不包含完整旧设备端、压测工具或新 OCRUN Agent。包内新增代码只有独立的 `mon_sensors_plugin/` 模块、独立 API 核心、新命令、安装器和文档，不包含 `ocrun/` 业务模块。

在被测设备停止监控和压测后，以管理员身份安装：

```sh
bash mon-sensors-plugin-0.12.8.run
# 非标准目录可显式指定
bash mon-sensors-plugin-0.12.8.run --app /root/ocrun --backend sckocp
```

第一条命令自动寻找唯一兼容 0730 目录，首次自动安装启用 sckocp，升级保留已有来源。第二条命令的 `/root/ocrun` 换成实际目录；两条任选一种。可追加 `--check` 只查看检查和计划，省略 `--check` 才安装。已运行监控、多个候选和不安全的目标会明确拒绝，不自动停任务。安装后：

- `/root/ocrun/mon-sensors-plugin` 是新增采集命令，模块放在同级 `mon-sensors-plugin.d/`。
- 原 `mon-sensors` 保留原采集功能，只有显式选择或持久选择 sckocp 时才转调插件。没有选择时默认 `legacy`。
- 原 `oct mon/killm/analyse/push` 继续使用，配置文件仍是 `.mon-sensors-backend`。
- 旧版适配目录 `sckocp-collector/` 如已存在会保留，新路径不再调用它。

直接调用插件采集一次：

```sh
/root/ocrun/mon-sensors-plugin --once
```

插件自带 `sckocp_api` 核心，无需再安装第三个包。它依赖已安装、激活的 sckocp，安装不会启动压测。完整参数、来源切换、升级恢复和权限要求见 [MON-SENSORS.md](../../monitoring/MON-SENSORS.md)。

0.12.8 / API 0.3.1 新增自动安装，保留上一版的可信程序路径检查、固定描述符执行、JSON 解析边界、私有日志权限及有限的暂时故障重试。以 root 采集时，sckocp 程序及其路径必须由 root 维护且不可被普通用户写入。原版 1.2.0 的单独云端验证记录见 `CLOUD-RESULTS.md`；这些改动不增强本体抵抗 root 修改的能力。

设备生成兼容旧格式的 `.mon` 和补充 JSON 日志，通过原 `oct push` 上传。Excel 应在设备执行 `oct analyse` 生成后一起上传。旧服务器分析器对全空列的汇总缺陷未修改；旧服务器也不会自动展示新增 JSON 字段。不要用新 OCRUN Agent 连接旧服务器，新旧任务协议不兼容。

## 独立本地接口

第三方软件独立使用时，以管理员身份执行：

```sh
bash sckocp-api-0.3.1.run
```

默认安装到 `/opt/sckocp-api` 并创建 `/usr/local/bin/sckocp-api`，支持 `--check`、`--prefix`、`--bin-dir`，重复执行可升级。`.tar.gz` 仍可单独解压使用。命令和 `from sckocp_api import collect` SDK 不依赖 OCRUN 或采集插件，不安装网络服务。

两种 `.run` 安装包都不需要访问网络，不自动安装系统依赖；缺少 Python 3.6+ 时明确提示。插件还需要标准路径中的 `python3` 命令。安装时不采集硬件、不修改 sckocp 或激活文件；包内校验只能检测损坏，应从可信渠道分发。安装包可通过已有内网文件传输方式下发，但本次未加入管理服务器的自动远程执行任务。

默认调用原版 `sckocp mon --json`，由 sckocp 本身完成激活与平台校验。接口不修改 sckocp 的程序、持久配置或激活文件；sckocp 自身的正常授权续期仍按原有方式运行。接口不会自行提权，也不增强原版本体对 root 修改或逆向的抵抗能力。使用条件、输出字段和失败状态见 [SCKOCP-API.md](../../monitoring/SCKOCP-API.md)。

原版 JSON 缺少部分指标、逐指标有效性和读数年龄。插件与接口保留缺失值，并明确标记质量未知；原程序报告的零也可能代表读取失败，不能把它直接当成硬件合格或温度保护的证据。

## 验证与部署范围

插件和接口的测试及构建在 GitHub Actions 云端 Linux 执行；原版管理归档仅复制和校验，不在本机运行包内程序。各版本实际完成的测试结果以仓库中的 `CLOUD-RESULTS.md` 和对应云端运行记录为准。

现有服务器的 `4.18.0-425.3.1.el8.x86_64` 是内核版本，本次不升级该服务器的系统或 OCRUN。云端模拟硬件及临时授权测试不等于客户真实设备、生产授权和传感器的实机验收。
